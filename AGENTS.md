# Agent Rules — Rule Library Index

> [!IMPORTANT]
> **Start at the repo-root [`AGENTS.md`](../AGENTS.md), not here.** That file is the portable entry point every agent should load: the project gate, the conventions that are always true, and a table telling you which rule to open for which task. This file is just the index of what lives in [`.agents/rules/`](./rules/).

**Do NOT preload all of these.** The library is ~1,650 lines, and in either project roughly a third of it describes the *other* one — Vue rules in a React repo, portal rules where there are no portals. Loading it all on every turn is the single largest avoidable context cost here, and wrong-project content in context is what causes agents to build to the wrong stack.

**Read a rule when the task touches it** (the root `AGENTS.md` table maps task → rule):

1. [Coding Standards](./rules/coding-standards.md) - Clean code, formatting, and DRY guidelines.
2. [Vue.js Standards](./rules/vue-standards.md) - Composition API, state, components. **Vue projects only** (see your project's profile).
3. [Laravel Standards](./rules/laravel-standards.md) - Controllers, models, FormRequests, migrations, routes.
4. [UI & Design Standards](./rules/ui-design.md) - Theme, colors, grids, dark mode, cards. **Portal-specific parts apply only to projects with portals.**
5. [Performance Standards](./rules/performance.md) - Lazy loading, memory cleanup, DB query scaling.
6. [Security Standards](./rules/security.md) - CSRF, input validation, policies, rate-limiting, encryption.
7. [Project Structure Standards](./rules/project-structure.md) - File and folder layouts across backend and frontend.
8. [Naming Convention Standards](./rules/naming-convention.md) - Casing for components, variables, tables, models, classes.
9. [Git Workflow Standards](./rules/git-workflow.md) - Branch names, Conventional Commits, the mandatory branch gate.
10. [Testing Standards](./rules/testing.md) - **Every backend and frontend change ships with a test that has run**: unit tests for pure logic, feature tests on a disposable `*_test` database for Handlers, Queries, endpoints and authorization, a schema test per migration, a regression test per fix, unit and component tests on the frontend. An app with no frontend runner gets one set up by the skill (Vitest for Vue / React + Vite, jest-expo for Expo), dev dependencies only. Binding on `webkit.implement`, `webkit.fix`, `webkit.refactor`, `webkit.migrate`.
11. [Documentation Standards](./rules/documentation.md) - Inline JSDoc/PHPDoc comments and API schemas.
12. [HRMS Domain Rules](./rules/hrms-rules.md) - Overtime, late logs, SSS/PhilHealth/Pag-IBIG, rate factors, portal separation. **Only for projects with payroll and timekeeping.**
13. [Execution Strategy](./rules/execution-strategy.md) - Workspace search order and scan optimization.
14. [Context Loading](./rules/context-loading.md) - Focus scoping and token safety limits.
15. [Duplicate Prevention](./rules/duplicate-prevention.md) - Logic and file reuse rules.
16. [Incremental Generation](./rules/incremental-generation.md) - Minimal diffs and safe file modification.
17. [Anti-Hallucination](./rules/anti-hallucination.md) - Constraints against fabricated routes, tables, or variables.
18. [System Awareness](./rules/system-awareness.md) - The canonical models/migrations/routes discovery scan. Update scan steps here only.
19. [Ticket Numbering](./rules/ticket-numbering.md) - The `T#####` convention: how a number is allocated **per project**, which skills may allocate, the eight fixed filenames inside the ticket folder (with the `task.md` upkeep, the fix pass, and when a ticket closes), and the ticket-named branch. **§8 covers the reverse direction** — a ticket passed as a command argument (`/webkit-fix F0135`) names a **branch on the remote that must be fetched and analyzed** before any work: the remote's live convention is `F####` (F0004 … F0174) alongside `T#####`, several branches can match one ticket (`F0135`, `F0135-fixed`, `f0135`), and `F0149-F0151` covers three. Read it before writing a spec or a report, before branching, or whenever a skill is invoked with a ticket.
20. [Project Profile](./rules/project-profile.md) - Verified ground-truth architecture for **both** codebases. Open it when you need detail beyond the root `AGENTS.md` summary — then read **only** your project's sections. Shared: top-level Query/Handler/Action (`App\Queries`, `App\Handlers`, `App\Actions` — `app/Domain/` is retired), no API Resources. Project-specific: database conventions (**opposite** in each), route organization, frontend layout, HTTP client.
21. [Authority Boundary](./rules/authority-boundary.md) - Every `/webkit-*` skill owns **only** its own workflow stage. A task that belongs to another stage is not done: the skill stops, reports `Authority boundary: <task> belongs to /webkit-<skill>. Not done here.`, and does not continue it — no compensating for another skill, no work outside its authority. Includes the table of which skill owns what.
22. [Versioning](./rules/versioning.md) - Semantic version detection after an implementation: classify each app's change from the spec and the diff (breaking → MAJOR, feature → MINOR, fix → PATCH, refactor/docs → none), compute the next version from the branch's base so re-runs never double-bump, and — per `versioning.mode` (`auto` / `recommend` / `off`) in `.agents/config/<project>.yml` — update the version files and build numbers and write a Keep a Changelog entry, or only recommend them. A fix is a PATCH only when the defect shipped in the base version; a fix to unreleased work on the same branch adds no bump. Never commits, tags, builds, or raises a server-side minimum version. Run by `/webkit-implement` and `/webkit-fix` as their last phase.

## Specs

Feature designs live in [.agents/specs/](./specs/) under their project, one **ticket folder** per feature — `T00001`, `T00002`, … allocated by `/webkit-specify` and holding all the documents for that work:

```text
.agents/specs/<project>/T00001/      # another project has its own T00001 — numbers are PER PROJECT
├── spec.md             ← /webkit-specify  (specs.md on tickets created before it)
├── plan.md             ← /webkit-specify  (executed and ticked by /webkit-implement)
├── task.md             ← /webkit-specify  (progress tracker; kept current by every later skill)
├── investigation.md    ← /webkit-investigate
├── refactor.md         ← /webkit-refactor
├── verify.md           ← /webkit-verify
├── code-review.md      ← /webkit-code-review
└── design-review.md    ← /webkit-design-review
```

A ticket does not need all eight. A feature ticket may have no `investigation.md`; a bug ticket usually has no spec and no plan. What is present tells you what has been done. **`/webkit-specify`, `/webkit-investigate`, and `/webkit-refactor` allocate a ticket** when their work has none — they are the three entry points; every other skill resolves the existing one.

The work is then implemented on a branch named after the ticket — bare `T00001`, matching the folder exactly, so any later skill can read the branch and find the spec. The format, the per-project increment, the fixed filenames, and the branch rule are canonical in [ticket-numbering.md](./rules/ticket-numbering.md) — read it before writing a spec or a report, or before branching.

Specs written before this convention still live in portal folders beside the ticket folders (`.agents/specs/<project>/<portal>/`); they remain valid and must still be found by spec discovery, so **search ticket folders and portal folders**. Ticket folder names carry no feature name — grep their contents (`grep -ril '<feature>' .agents/specs/<project> --include='*.md'`), not their names.

**When a spec exists for the feature you're building, it is the primary source of truth** — `webkit.implement` reads it, executes its `plan.md` task by task, and builds to it (tables, queries, handlers, routes, API contract on the backend; layout, components, filters, pagination, types on the frontend). The spec supersedes ad-hoc design decisions; only a rule in [.agents/rules/](./rules/) overrides it, and any genuine conflict should be flagged.

## Workflow Skills

For end-to-end feature work, prefer the skills in [.agents/skills/](./skills/) over ad-hoc edits — they encode the rules above into a concrete sequence:

1. [webkit.specify](./skills/webkit.specify/SKILL.md) - **Specification phase.** Turns a feature request into one implementation-ready blueprint from [the feature-specification template](./template/feature-specification.md), grounded in the real project, before any code is written. Allocates the ticket and writes two files into it: `spec.md` (WHAT) — the locked source of truth the implement and review skills build to and check against — and `plan.md` (HOW / IN WHAT ORDER) from [the implementation-plan template](./template/implementation-plan.md): reuse map, file change map, and file-by-file tasks that `webkit.implement` executes and ticks off. Also creates `task.md` from [the task-tracker template](./template/task-tracker.md): one page showing which tasks are done, which findings are open, what the ticket waits on, and a log of each skill run, kept current by every later skill. Minor corrections update them in place; only a major change creates a new version. `/webkit-specify T##### --plan` adds a plan to an older spec. Never edits application code.
2. [webkit.investigate](./skills/webkit.investigate/SKILL.md) - **Investigates bugs and other problems whose cause must be found** — regressions, performance, security, data integrity, integrations, environment / build failures. Reproduces where possible, traces a single root cause with file:line evidence, records every hypothesis checked, measures the impact (files, data, endpoints, users), and recommends the minimal safe fix with a fix plan. Not for feature planning (`webkit.specify`) or diff review (`webkit.code-review`). Never edits code or data; allocates the ticket and writes `investigation.md` from [the investigation-report template](./template/investigation-report.md) for `webkit.fix` to apply.
3. [webkit.implement](./skills/webkit.implement/SKILL.md) - **Implements an approved spec by executing its `plan.md`** task by task (ticking each, so a later session resumes where this one stopped), backend first (migrations, models, Query/Handler/Action classes, controllers, routes, validation, authorization) and then frontend integration (pages, components, state, api layer, loading / error / empty states). Follows the existing architecture and reuses existing code before creating anything, recording the search behind every new file. Never adds requirements, expands scope, or edits the spec; stops with "Specification clarification required" when the spec is incomplete. Ends with SemVer detection per app ([versioning.md](./rules/versioning.md): bump + CHANGELOG in `auto` mode, a recommendation in `recommend`) and an implementation summary of reused components, new files, updated files, and the version result.
4. [webkit.fix](./skills/webkit.fix/SKILL.md) - **Implements the approved fixes from one report**: `/webkit-fix <ticket> --code-review | --verify | --investigation | --refactor | --design-review`. The report is the source of truth — CRITICAL / HIGH from code-review and design-review, BLOCKER / REQUIRED FIX from verify, the fix plan from an investigation — applied with the smallest safe change on the ticket's existing branch, then regression-checked. Never re-reviews, never adds findings or requirements; an unrelated problem is reported as "Additional issue discovered", not fixed. Then runs SemVer detection per [versioning.md](./rules/versioning.md) (PATCH + CHANGELOG "Fixed" line for a defect that shipped; no bump for a fix to unreleased work on the same branch), and **closes the loop**: marks each finding `✅ FIXED` in the source report with the evidence and recomputes its status as a fix pass, ticks `plan.md` and `task.md`, records the fixes in the spec's §14 Review findings, and sets the ticket `Done` when it is finished — so the review does not have to be re-run just to confirm the fixes. Ends with a Fix Summary marked FIX COMPLETED or PARTIALLY COMPLETED.
5. [webkit.refactor](./skills/webkit.refactor/SKILL.md) - **Behavior-preserving restructuring** toward a stated goal (or named code-review maintainability findings): removes duplication, moves logic into the project's Query / Handler / component patterns, consolidates local copies into the design system, deletes dead code. Runs the project's own checks before and after, and records what moved where, the duplication removed, and the regression evidence in `refactor.md` from [the refactor-report template](./template/refactor-report.md), with a status of BEHAVIOR PRESERVED / PRESERVED WITH UNVERIFIED AREAS / REGRESSION DETECTED. Never fixes bugs, adds features, changes APIs or schema, or edits the spec.
6. [webkit.migrate](./skills/webkit.migrate/SKILL.md) - Migrates a feature FROM the repo you are in INTO the sibling target project you name and **implements it there**, matching the target's conventions. Two paths: `/webkit-migrate <source_path> <target_path>`; with no target path it asks, never picks one. Flow is the invariant (data, API, rules, state machine identical); stack is the variable (framework, state, HTTP client, UI library, backend layout follow the target). Read-only on the source; writes the portable contract to `.agents/migrations/` from [the migration-contract template](./template/migration-contract.md), implements into the target backend first, verifies parity, and ends with a [migration summary](./template/migration-summary.md) marked MIGRATION COMPLETED (parity confirmed) or PARTIALLY COMPLETED.
7. [webkit.verify](./skills/webkit.verify/SKILL.md) - **ADVERSARIAL review against the spec.** Checks the finished implementation against its `spec.md` — scope, user flow, technical design, every acceptance criterion, edge cases, security — then tries to break it (functional, edge-case, security, performance, maintainability). Every claim needs `file:line` evidence, and the absence sweep hunts rules that were never coded. Findings are BLOCKER / REQUIRED FIX / IMPROVEMENT / OUT OF SCOPE; the result is PASS / PASS WITH FIXES / FAILED with a READY FOR MERGE / FIX REQUIRED BEFORE MERGE recommendation. No scope expansion, and the spec changes only for a spec error or an approved requirement change — never for a bug fix. Never edits code; writes `verify.md` into the ticket folder from [the verification-report template](./template/verification-report.md) and hands BLOCKER and REQUIRED FIX findings to `webkit.fix`. Then keeps the ticket in step: applies a proven spec error (Case 1) to `spec.md` and `plan.md` itself, ticks plan tasks it proved done, and updates `task.md`; only a requirement change (Case 2) goes back to `webkit.specify`.
8. [webkit.code-review](./skills/webkit.code-review/SKILL.md) - **Senior-developer review of the diff** (a ticket's branch, a branch vs its base, or uncommitted changes): correctness, bug prevention, performance with measurable impact, security, maintainability, and fit with the existing architecture — judged against the rules above, never personal preference. Each finding is CRITICAL / HIGH / MEDIUM / LOW / INFO with file, line, and a concrete fix; the change is rated APPROVED / APPROVED WITH COMMENTS / CHANGES REQUIRED with a READY TO MERGE / FIX REQUIRED recommendation. Complements `webkit.verify`: verify asks *does this match the spec*, this asks *is this code any good*. No scope expansion, and it never touches the spec — a requirement question is reported as "Specification clarification required". Never edits code; writes `code-review.md` into the change's ticket folder from [the code-review-report template](./template/code-review-report.md) (or to `.agents/reports/` when the change has no ticket).
9. [webkit.design-review](./skills/webkit.design-review/SKILL.md) - **Senior-designer review of the visual layer** — components, theme tokens, class strings — in two strictly separated halves: a **Fit Review** graded CRITICAL / HIGH / MEDIUM / LOW / INFO against [ui-design.md](./rules/ui-design.md) and the real tokens (accents, WCAG AA contrast, dark-mode parity, component reuse, layout, motion), each finding naming what the user sees and a concrete fix; and optional, grounded **Modern Enhancement Ideas** that never contradict a rule and never change the verdict. Rates the change APPROVED / APPROVED WITH COMMENTS / CHANGES REQUIRED with a READY TO MERGE / FIX REQUIRED recommendation. Complements `webkit.code-review`: that one asks *is this code any good*, this asks *does this look right, and could it look better* — when both run, code-review defers its visual findings here. Never edits code, theme files, or specs; writes `design-review.md` into the ticket folder from [the design-review-report template](./template/design-review-report.md).
10. [webkit.document](./skills/webkit.document/SKILL.md) - Writes the **feature guide** for a page that has already been built: a plain-language half anyone can follow (what it does, the menu path, a **mermaid diagram** of the journey or approval flow, numbered step-by-step of what you see and click, the rules that decide what appears, what to do when it looks wrong), then an *Under the hood* half with the data sources, route table, architecture diagram, and file links. Every on-screen label and route is verified against the real template, so the guide describes **what shipped, not what was specced** — including a required Known issues section. Never edits code; writes `.agents/docs/<feature>.md` from [the feature-guide template](./template/feature-guide.md), **one guide per feature, updated in place forever** — not a ticket file, because a guide outlives the ticket.

**Typical spec-driven flow:** `webkit.specify` allocates the ticket folder and writes `.agents/specs/<project>/T#####/spec.md` + `plan.md` + `task.md` → `webkit.implement` branches on `T#####`, executes `plan.md`, and builds the **backend first, then integrates the frontend** → **`webkit.verify` proves the result actually matches the spec**, **`webkit.code-review` checks the diff is good code** (`webkit.design-review` for the visual layer) → `webkit.fix` (which marks the findings fixed in the report, so no re-review) or `webkit.refactor` as needed → `webkit.document` writes the feature guide once the page is real. (`webkit.investigate` up front for bug/RCA work.)

> [!IMPORTANT]
> **Every implementing skill starts with a BLOCKING branch gate.** `webkit.implement`, `webkit.fix`, and `webkit.refactor` must run the [Mandatory Branch Gate](./rules/git-workflow.md#mandatory-branch-gate-for-implementing-skills) and **create** a branch before touching a file — not merely confirm one is needed. Committing stays the user's call; the gate only guarantees the work is isolated and revertible.
>
> `webkit.verify` is the gate that keeps spec-driven development honest. Without it, "the spec was implemented" is an assumption nobody ever tested — which is exactly how a feature drifts from its own blueprint. Run it before considering a spec done.
