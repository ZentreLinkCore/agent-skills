### 3.3 Messaging

The Messaging module will provide users with real-time communication capabilities through direct and group conversations. It will allow users to send, receive, manage, and interact with messages while maintaining appropriate access controls and conversation privacy.

#### 3.3.1 Conversation Management

The system shall allow authenticated users to access conversations in which they are participants.

The system shall support:

* Creating a direct conversation.
* Opening an existing conversation.
* Viewing conversation participants.
* Viewing conversation history.
* Managing supported conversation settings.
* Leaving group conversations where permitted.
* Starting or accessing message threads.

The system shall prevent users from accessing conversations in which they do not have the required membership or permission.

#### 3.3.2 Sending Messages

Users shall be able to send messages to conversations where they have permission to participate.

The system shall:

1. Accept message content from the authenticated user.
2. Validate the message before processing.
3. Associate the message with the authenticated sender.
4. Associate the message with the appropriate conversation.
5. Store the message.
6. Generate the appropriate real-time event.
7. Deliver the message update to authorized connected participants.

A successfully sent message shall contain information such as:

* Message identifier
* Conversation identifier
* Sender identifier
* Message content
* Creation timestamp
* Message type
* Optional metadata

#### 3.3.3 Message Types

The messaging system may support multiple message types, including:

* Text
* Image
* Video
* Audio
* File
* System message
* Reply
* Other supported rich-content messages

Each message type shall have appropriate validation and processing rules.

#### 3.3.4 Real-Time Message Delivery

Messages shall be delivered to connected conversation participants in real time.

The expected flow is:

**Sender → Backend API → Message Storage → Real-Time Event → Authorized Recipients**

The system shall ensure that real-time events are delivered only to users authorized to access the corresponding conversation.

The real-time communication layer may use Pusher as the primary provider during development and deployment, while an alternative provider such as Laravel Reverb may be used as a development fallback where appropriate.

#### 3.3.5 Message Editing

The system shall allow users to edit their own messages where editing is supported.

When a message is edited, the system shall:

1. Verify that the authenticated user owns the message or has the required permission.
2. Validate the updated content.
3. Update the stored message.
4. Record that the message has been edited where applicable.
5. Broadcast the updated message state to authorized participants.

The client interface may indicate that a message has been edited.

#### 3.3.6 Message Deletion

The system shall allow users to delete their own messages where permitted.

Depending on the final design, deletion may be implemented as:

* Soft deletion
* Content removal while preserving the message record
* Permanent deletion

The selected approach shall be documented as part of the final database and data-retention design.

When a message is deleted, authorized participants shall receive the appropriate real-time update.

#### 3.3.7 Message Reactions

Users shall be able to react to messages using supported reaction types.

The system shall:

1. Verify that the user can access the message.
2. Add or remove the user's reaction.
3. Prevent unintended duplicate reactions according to the selected reaction rules.
4. Update reaction counts.
5. Broadcast reaction changes in real time.

The system shall maintain the relationship between the user, message, and reaction.

#### 3.3.8 Replies and Threads

The system shall support replies and threaded conversations.

Users shall be able to reply to a specific message without requiring the reply to become a separate unrelated conversation.

A thread may contain:

* The original parent message.
* One or more replies.
* Reply authors.
* Reply timestamps.
* Message reactions.
* Other supported message interactions.

Thread updates shall be synchronized with authorized conversation participants.

#### 3.3.9 Mentions

The system shall support user mentions within messages where enabled.

A mention may identify another user using a supported format such as:

`@username`

When a user is mentioned, the system may:

1. Identify the mentioned user.
2. Store the mention relationship.
3. Highlight the mention in the client interface.
4. Generate a notification for the mentioned user.
5. Deliver the relevant update through the real-time communication layer.

The system shall validate mentions to prevent invalid or unauthorized references.

#### 3.3.10 Typing Indicators

The system shall provide real-time typing indicators for active conversations.

When a user begins typing, the client may send a temporary typing event to the backend or real-time service. Other authorized participants may then receive an indication that the user is typing.

Typing indicators shall be treated as temporary real-time state and should not be unnecessarily persisted as permanent database records.

The system shall also handle cases where a user stops typing, leaves the conversation, disconnects, or experiences a connection interruption.

#### 3.3.11 Read and Unread States

The system shall support message read states where applicable.

The system may maintain information such as:

* Whether a conversation contains unread messages.
* The latest message read by a user.
* The timestamp when a conversation was last read.

Read-state updates may be transmitted through real-time events when required.

#### 3.3.12 Message Attachments

The system may allow users to attach supported files and media to messages.

The system shall:

1. Validate file type.
2. Validate file size.
3. Apply appropriate security checks.
4. Store the file using an appropriate storage mechanism.
5. Associate the attachment with the corresponding message.
6. Restrict unauthorized access to private attachments.

The application shall not expose private attachment resources to users who are not authorized to access the associated conversation.

#### 3.3.13 Message Formatting

The system may support rich message formatting where appropriate.

Supported formatting may include:

* Bold text
* Italic text
* Links
* Mentions
* Code blocks
* Inline code
* Other supported formatting

User-generated content shall be processed safely to prevent malicious content from being executed as application code.

#### 3.3.14 Message Pagination and History

The system shall support retrieving historical messages from conversations.

To improve performance, messages should be retrieved using pagination or another appropriate incremental loading mechanism rather than loading the entire conversation history at once.

The system may support:

* Initial message loading.
* Loading older messages.
* Loading newer messages.
* Jumping to a specific message.
* Loading thread history separately.

#### 3.3.15 Conversation Search

The system may allow users to search messages within conversations they are authorized to access.

Search results may include:

* Message content.
* Sender.
* Conversation.
* Timestamp.
* Message type.

Search functionality shall respect conversation membership and access permissions.

#### 3.3.16 Message Notifications

The system may generate notifications for relevant messaging events, including:

* New direct messages.
* New group messages.
* Mentions.
* Replies.
* Thread activity.
* Reactions where notification is enabled.

Users shall be able to configure supported notification preferences.

#### 3.3.17 Message Delivery and Connection Recovery

The system shall account for temporary network interruptions.

If a user temporarily loses their real-time connection, the system shall provide mechanisms for restoring the connection and retrieving missed updates where supported.

The system shall treat the backend database as the authoritative source for persistent message data. Real-time events are primarily used to notify connected clients about changes.

This distinction ensures that a temporary WebSocket or real-time provider failure does not automatically result in permanent message loss.

#### 3.3.18 Messaging Security

The messaging system shall enforce appropriate security controls.

The system shall:

1. Authenticate users before accessing protected conversations.
2. Verify conversation membership before returning messages.
3. Verify message ownership before allowing protected modifications.
4. Validate all message content and attachments.
5. Protect private conversations from unauthorized access.
6. Apply rate limits where appropriate.
7. Prevent malicious content from being executed.
8. Protect private attachment resources.
9. Avoid exposing internal security credentials through message-related APIs.
