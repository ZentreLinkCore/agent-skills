### 3.7 Jam

The Jam module will allow multiple users to listen to music together in a synchronized session. A Jam session is a shared listening environment where a host and participating users can listen to the same supported music track while maintaining synchronized playback states.

The Jam feature will build upon the Music, Realtime Communication, Authentication, and User Management modules.

The system will synchronize playback information such as the current track, playback status, playback position, and playback timestamps. The actual music audio will not be transmitted through the application's backend or real-time messaging infrastructure. Instead, participating clients will use the supported playback mechanism of the selected music provider.

#### 3.7.1 Jam Session Creation

An authenticated user shall be able to create a Jam session.

When creating a Jam session, the system may generate:

* Unique Jam identifier
* Jam name
* Host identifier
* Session status
* Current track
* Playback state
* Creation timestamp
* Participant configuration
* Access or privacy settings

The user who creates the Jam shall initially become the Jam Host.

#### 3.7.2 Jam Session Joining

Authenticated users shall be able to join an available Jam session.

A user may join through:

* Jam invitation
* Shared Jam link
* Community
* Direct message
* Search or discovery where supported

Before joining, the system shall validate whether the user is authorized to access the Jam session.

After joining, the participant shall receive the current Jam state and synchronize their local player with the active session.

#### 3.7.3 Jam Participants

A Jam session may contain multiple participants.

The system shall maintain participant information such as:

* User identifier
* Display name
* Profile image
* Join time
* Current connection state
* Participant role
* Playback synchronization state where applicable

The system shall update participant presence when users join, leave, disconnect, or reconnect.

#### 3.7.4 Jam Host

The Jam Host shall manage the primary playback state of the session.

Depending on the configured permissions, the Host may:

* Start playback
* Pause playback
* Resume playback
* Seek
* Change the current track
* End the Jam
* Manage participant permissions

The system may support additional playback controllers in future versions.

#### 3.7.5 Jam Participant Permissions

The system shall support configurable participant permissions.

For example, a Jam may use:

**Host-controlled mode**

Only the Jam Host can control playback.

**Collaborative mode**

Participants with appropriate permissions may also control playback.

The backend shall enforce these permissions through authorization rules rather than relying solely on frontend controls.

#### 3.7.6 Jam Playback State

The system shall maintain the current playback state of the Jam.

The playback state may contain:

* Current track identifier
* Playback status
* Current playback position
* Server timestamp
* Host identifier
* Playback version or state identifier
* Last synchronization timestamp

Example:

```json id="gq0g3n"
{
    "track_id": "track-123",
    "status": "playing",
    "position": 42.35,
    "server_timestamp": 1790000000000
}
```

This information allows newly joined or reconnected participants to determine the current playback position.

#### 3.7.7 Jam Playback Events

The system shall generate real-time events whenever the shared playback state changes.

Possible events include:

* `jam.created`
* `jam.joined`
* `jam.left`
* `jam.play`
* `jam.pause`
* `jam.seek`
* `jam.track_changed`
* `jam.ended`
* `jam.state_updated`

These events shall be delivered through the application's real-time communication layer.

For the initial implementation, Pusher may be used as the primary real-time provider, with Laravel Reverb available as a development fallback where configured.

#### 3.7.8 Play Synchronization

When the Host starts playback, the system shall distribute the playback state to connected participants.

A simplified flow is:

**Host presses Play**

→ Client sends playback command
→ Laravel validates the request
→ Jam state is updated
→ Real-time event is broadcast
→ Participants receive the event
→ Participants calculate the target playback position
→ Local players begin or resume playback

The system shall use timestamps and playback positions to reduce differences between participants.

#### 3.7.9 Pause Synchronization

When the active playback is paused, the system shall broadcast the updated paused state.

The event may contain:

```json id="v5fr2n"
{
    "event": "jam.pause",
    "track_id": "track-123",
    "position": 85.20,
    "server_timestamp": 1790000040000
}
```

Participants shall update their local players to the specified playback position and pause playback.

#### 3.7.10 Seek Synchronization

When the Host seeks to another position, the system shall broadcast the new playback position.

For example:

```json id="2m8y4k"
{
    "event": "jam.seek",
    "track_id": "track-123",
    "position": 120.50,
    "server_timestamp": 1790000060000
}
```

Participants shall update their local playback position according to the received state.

#### 3.7.11 Track Change Synchronization

When the active track changes, the system shall notify all connected participants.

The event may contain:

* Previous track identifier
* New track identifier
* New playback position
* Playback status
* Server timestamp

Participants shall load the new track using the supported music provider integration and synchronize playback according to the Jam state.

#### 3.7.12 New Participant Synchronization

A participant joining an active Jam shall not need to wait for another playback event before synchronizing.

After joining, the system shall provide the current Jam playback state.

For example:

```text id="f6t2n1"
Current Track: Track A
Status: Playing
Position: 128.42 seconds
Server Timestamp: 1790000100000
```

The participant's client can use this information to calculate the expected current position before starting local playback.

#### 3.7.13 Playback Drift Correction

Network conditions may cause participants' playback positions to gradually become different.

The system may therefore implement periodic synchronization.

For example:

```text id="n8c2v7"
Expected Position: 180.50s
Local Position:    179.92s
Difference:          0.58s
```

Depending on the difference, the client may:

* Continue playback without correction
* Gradually adjust playback timing
* Seek to the expected position
* Request a fresh Jam state

The correction threshold shall be configurable during implementation.

#### 3.7.14 Reconnection Handling

The system shall support participants reconnecting after temporary network interruptions.

When a participant reconnects, the client shall:

1. Re-establish the real-time connection.
2. Authenticate the connection.
3. Rejoin the appropriate Jam channel.
4. Request or receive the latest Jam state.
5. Compare the local playback state with the current session state.
6. Correct the local player if necessary.

The system shall prioritize the latest valid Jam state over stale local playback information.

#### 3.7.15 Host Disconnection

If the Jam Host disconnects unexpectedly, the system shall detect the change in host presence.

The system may implement one of the following behaviors:

* Pause the Jam temporarily.
* Allow the Jam to continue using the last known state.
* Automatically transfer Host privileges to another participant.
* End the Jam after a configured timeout.

The initial implementation may use a defined host-disconnection policy, while automatic host migration may be introduced in a future version.

#### 3.7.16 Jam Session Ending

The Host or an authorized user shall be able to end a Jam session.

When a Jam ends:

* The Jam status shall be updated.
* Participants shall receive a `jam.ended` event.
* Active playback may be stopped or returned to individual playback.
* The Jam channel may become inactive.
* The session may be recorded in the user's Jam history where supported.

#### 3.7.17 Jam Privacy

The system shall support access controls for Jam sessions.

Possible privacy options include:

* Public
* Community-only
* Invite-only
* Private

The backend shall verify access permissions before allowing a user to join a protected Jam session.

#### 3.7.18 Jam Real-Time Architecture

The Jam module shall use the real-time infrastructure for state synchronization rather than audio transmission.

The architecture can be represented as:

```text
                 ┌─────────────────┐
                 │    Jam Host     │
                 │   Music Player  │
                 └────────┬────────┘
                          │
                     Playback Event
                          │
                          ▼
                 ┌─────────────────┐
                 │  Laravel API    │
                 │  Jam Service    │
                 └────────┬────────┘
                          │
                   Jam State Update
                          │
                          ▼
                 ┌─────────────────┐
                 │     Pusher      │
                 │  Realtime Layer │
                 └─────┬───┬───┬───┘
                       │   │   │
              ┌────────┘   │   └────────┐
              ▼            ▼            ▼
          Participant   Participant   Participant
          Music Player  Music Player  Music Player
```

The real-time layer transmits synchronization information rather than the music audio itself.

#### 3.7.19 Jam and Music Provider Separation

The Jam module shall remain independent from the specific music provider.

The architecture shall separate:

**Music Provider**

Responsible for:

* Music catalog
* Track metadata
* Supported playback

**Jam Service**

Responsible for:

* Session management
* Participant management
* Playback state
* Authorization
* Synchronization events
* Reconnection handling

**Realtime Service**

Responsible for:

* Event delivery
* Presence
* Connection management

This separation allows the system to change music providers without redesigning the entire Jam architecture.

#### 3.7.20 Jam Security

The system shall enforce authorization for Jam operations.

Security controls may include:

* Authentication
* Jam membership validation
* Host authorization
* Participant permissions
* Private channel authorization
* Rate limiting
* Request validation
* Secure real-time connections

Clients shall not be trusted to determine whether a user is allowed to control a Jam.

#### 3.7.21 Jam Performance Requirements

The Jam module should minimize unnecessary real-time traffic.

The system should avoid continuously broadcasting playback position at very high frequencies.

Instead, the system should primarily broadcast state-changing events such as:

* Play
* Pause
* Seek
* Track change
* Join
* Leave
* Synchronization updates

Clients should calculate intermediate playback positions locally whenever possible.

This approach reduces real-time traffic while maintaining synchronized playback.

#### 3.7.22 Jam Error Handling

The system shall handle Jam-related errors including:

* Invalid Jam identifier
* Unauthorized access
* Jam no longer available
* Track unavailable
* Provider playback failure
* Real-time connection failure
* Host disconnection
* Synchronization failure
* Participant reconnection

Users shall receive appropriate feedback when a Jam operation cannot be completed.
