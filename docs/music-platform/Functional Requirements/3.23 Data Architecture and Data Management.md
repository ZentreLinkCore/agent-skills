### 3.23 Data Architecture and Data Management

The Data Architecture and Data Management module shall define the structure, organization, relationships, lifecycle, integrity, and management of data used by the Social Music and Community Platform.

The data architecture shall support the major functional areas of the system, including user accounts, messaging, communities, music, Jam sessions, notifications, files, security, and audit logs.

The system shall use a relational database as the primary source of persistent application data. PostgreSQL is the proposed primary database for the initial architecture.

#### 3.23.1 Data Architecture Objectives

The data architecture shall aim to:

* Maintain consistent and reliable application data.
* Minimize unnecessary data duplication.
* Define clear relationships between entities.
* Support efficient querying.
* Protect sensitive information.
* Support increasing data volume.
* Enable reliable transactions.
* Support backups and recovery.
* Maintain data ownership and access boundaries.
* Support future application expansion.

#### 3.23.2 Primary Database

The proposed primary relational database is PostgreSQL.

The database shall contain persistent application information such as:

* Users
* Profiles
* Conversations
* Messages
* Reactions
* Communities
* Channels
* Memberships
* Notifications
* Jam sessions
* Music metadata where permitted
* File metadata
* Audit records
* User settings

The final database implementation may evolve according to operational requirements.

#### 3.23.3 High-Level Data Model

The primary relationships may be represented as:

```text id="n4m8q2"
User
 │
 ├── Profile
 ├── Settings
 ├── Conversations
 ├── Communities
 ├── Notifications
 ├── Files
 ├── Jam Memberships
 └── Audit Activity
       │
       ▼
Conversation
 │
 ├── Members
 └── Messages
       │
       ├── Reactions
       ├── Replies
       ├── Mentions
       └── Attachments

Community
 │
 ├── Members

       │
       └── Messages

Jam
 │
 ├── Host
 ├── Members

```

#### 3.23.4 Entity Identification

Major entities shall have unique identifiers.

Examples include:

```text id="c7r3m9"
users.id
conversations.id
messages.id
communities.id
channels.id
jams.id
notifications.id
files.id
audit_logs.id
```

The identifier strategy shall be consistent throughout the system.

#### 3.23.5 Primary Keys

Each persistent entity shall have a primary key.

Primary keys shall:

* Uniquely identify records.
* Remain stable during the record lifecycle.
* Be indexed.
* Be referenced by related entities where required.

The final identifier type may use integers, UUIDs, ULIDs, or another strategy based on system requirements.

#### 3.23.6 Foreign Keys

Relationships between entities shall use foreign keys where appropriate.

Example:

```text id="j8p4w6"
messages
    conversation_id ─────► conversations.id
    sender_id ───────────► users.id
```

Foreign-key relationships shall help preserve referential integrity.

#### 3.23.7 User Data

The `users` entity shall contain core account information.

Potential fields include:

```text id
email
username
password_hash
status
email_verified_at
last_login_at
created_at
updated_at
deleted_at
```

Authentication secrets shall be stored using secure password hashing mechanisms.

#### 3.23.8 Profile Data

Profile information shall be separated from core authentication data where appropriate.

Potential information includes:

```text id="x5m9q3"
user_id
display_name
username
bio
profile_image
status_message
visibility
created_at
updated_at
```

The final schema may combine or separate these structures depending on implementation requirements.

#### 3.23.9 User Settings

User preferences shall be stored separately or in an appropriate structured settings model.

Settings may include:

* Privacy
* Notifications
* Appearance
* Accessibility
* Playback
* Messaging
* Jam preferences
* Language
* Session preferences

Sensitive settings shall be protected using the same authorization rules as other user data.

#### 3.23.10 Conversation Data

A conversation represents a communication context.

It may represent:

* Direct conversation
* Group conversation

Potential fields include:

```text id
type
name
created_by
created_at
updated_at
```

Conversation membership shall be stored separately to support multiple participants.

#### 3.23.11 Conversation Membership

The `conversation_members` entity shall represent the relationship between users and conversations.

Potential fields include:

```text id
conversation_id
user_id
role
joined_at
left_at
muted_at
last_read_at
```

This allows membership-specific information to be maintained independently from the conversation.

#### 3.23.12 Message Data

The `messages` entity shall contain persistent messages.

Potential fields include:

```text id
conversation_id
sender_id
parent_message_id
message_type
content
metadata
created_at
updated_at
deleted_at
```

Message data shall support replies, threads, edits, and deletion behavior.

#### 3.23.13 Message Relationships

A message may be associated with:

* Sender
* Conversation
* Parent message
* Reactions
* Mentions
* Attachments
* Read states
* Thread replies

Example:

```text id="m3r8k5"
Message
 │
 ├── Sender
 ├── Conversation
 ├── Parent Message
 ├── Reactions
 ├── Mentions
 ├── Attachments
 └── Replies
```

#### 3.23.14 Message Reactions

Reactions shall be stored separately from message content.

Potential fields include:

```text id
message_id
user_id
reaction
created_at
```

A unique constraint may prevent the same user from creating duplicate instances of the same reaction on one message where that behavior is required.

#### 3.23.15 Message Mentions

Mentions may be stored separately to support notification and discovery functionality.

Potential fields include:

```text id
message_id
mentioned_user_id
created_at
```

This allows the system to identify users mentioned in a message without parsing the message repeatedly.

#### 3.23.16 Message Read State

Read information may be represented through conversation membership or a dedicated read-state entity.

Potential data includes:

```text user_id
conversation_id
last_read_message_id
last_read_at
```

The final implementation should avoid creating unnecessary records for every message read event when a simpler cursor-based approach is sufficient.

#### 3.23.17 Thread Data

Threads may be represented using a parent-child message relationship.

Example:

```text id="q8c4n7"
Parent Message
      │
      ├── Reply 1
      ├── Reply 2
      └── Reply 3
```

The `parent_message_id` field may identify the root or parent message depending on the selected implementation.

#### 3.23.18 Community Data

A community represents a larger organized social space.

Potential fields include:

```text id
owner_id
name
description
image
visibility
status
created_at
updated_at
```

Community membership and roles shall be stored separately.

#### 3.23.19 Community Membership

The `community_members` entity shall define user participation in a community.

Potential fields include:

```text id
community_id
user_id
role
status
joined_at
created_at
updated_at
```

Roles may include:

```text
Owner
Administrator
Moderator
Member
```

#### 3.23.20 Channel Data

Channels belong to communities.

Potential fields include:

```text id
community_id
name
type
description
visibility
created_by
created_at
updated_at
```

Channel types may include:

* Text
* Announcement
* Private

#### 3.23.21 Channel Access

Private channel access shall be controlled through appropriate membership relationships.

The system shall not rely solely on frontend visibility to protect private channels.

Backend authorization shall determine whether a user can access channel data.

#### 3.23.22 Notification Data

Persistent notifications shall be stored in the database.

Potential fields include:

```text id
user_id
type
title
message
data
read_at
created_at
```

Notification data may reference another resource through structured metadata.

#### 3.23.23 Jam Data

The `jams` entity shall represent a shared listening session.

Potential fields include:

```text id
host_id
name
privacy
status
current_track_id
created_at
started_at
ended_at
```

Jam membership shall be represented separately.

#### 3.23.24 Jam Membership

The `jam_members` entity shall contain users participating in a Jam.

Potential fields include:

```text id
jam_id
user_id
role
joined_at
left_at
```

The role may distinguish:

```text
Host
Participant
```

Additional permissions may be added if collaborative control is introduced.

#### 3.23.25 Jam Playback State

The current playback state shall be stored separately from Jam membership.

Potential information includes:

```text id
jam_id
track_id
status
position
server_timestamp
state_version
updated_at
```

The database state provides persistent recovery information while realtime events provide immediate updates.

#### 3.23.26 Jam State Versioning

Playback states may use a version number or sequence value.

Example:

```text id="v6k2m8"
state_version = 41
```

When a newer state is received, clients can determine whether an incoming event is older than the current state.

This can help prevent stale events from overwriting newer playback information.

#### 3.23.27 Music Data

Music data shall be designed around the selected external provider.

The application may store permitted metadata such as:

* Provider
* Provider track ID
* Track title
* Artist
* Album
* Artwork reference
* Duration
* Metadata timestamps

The system shall not store protected audio content unless the relevant provider and licensing terms explicitly permit it.

#### 3.23.28 Provider Independence

Music records should identify their provider.

Example:

```text id="r3n8q5"
provider = "provider_a"
provider_track_id = "track-123"
```

This allows the music abstraction layer to support future providers.

#### 3.23.29 File Metadata

Files should be represented through metadata records rather than storing large binary content directly inside relational database tables.

Potential fields include:

```text id
user_id
storage_key
original_name
mime_type
size
visibility
created_at
deleted_at
```

The actual file may be stored in local or object storage.

#### 3.23.30 Attachment Relationships

A file may be attached to a message through an attachment relationship.

```text id="k4m7p2"
Message
   │
   └── Message Attachment
          │
          └── File
```

This allows the same storage system to support different application features.

#### 3.23.31 Audit Data

Audit logs shall be stored separately from ordinary application activity.

Potential fields include:

```text id
actor_id
action
resource_type
resource_id
result
metadata
created_at
```

Audit data shall be protected against unauthorized modification.

#### 3.23.32 Database Normalization

The database should generally follow relational normalization principles.

Normalization shall help reduce:

* Duplicate information
* Update anomalies
* Inconsistent values
* Unnecessary storage

Denormalization may be introduced selectively when performance measurements justify it.

#### 3.23.33 Controlled Denormalization

Examples of potential denormalized data include:

* Cached message counts
* Unread counts
* Community member counts
* Conversation last-message summaries
* Search indexes

Denormalized values shall have clearly defined update and recovery behavior.

#### 3.23.34 Data Integrity

The system shall use multiple layers of data-integrity protection.

These may include:

* Database constraints
* Foreign keys
* Unique constraints
* Check constraints
* Application validation
* Authorization
* Transactions

Application validation shall not replace database integrity controls.

#### 3.23.35 Transactions

Database transactions shall be used for operations that require multiple related changes to succeed together.

Example:

```text id="w7r3m9"
Create Message
     │
     ├── Save Message
     ├── Save Mentions
     ├── Save Attachments
     └── Create Notification
```

Where appropriate, related database operations shall be committed atomically.

#### 3.23.36 Transaction Boundaries

Transactions should remain appropriately scoped.

Long-running external operations should generally not be performed inside database transactions when avoidable.

For example, external music-provider requests should not hold a database transaction open unnecessarily.

#### 3.23.37 Event and Transaction Consistency

Realtime events should be published only when the corresponding persistent state is safely committed.

Where appropriate, event dispatching should occur after successful database commit.

This helps prevent clients from receiving an event for data that was later rolled back.

#### 3.23.38 Idempotency

Important operations should support idempotency where duplicate requests are possible.

Examples include:

* Message submission
* File upload finalization
* Payment-related operations if introduced later
* Jam control events
* Notification creation

Idempotency mechanisms may use request identifiers or unique constraints.

#### 3.23.39 Soft Deletion

Soft deletion may be used for entities where recovery, auditability, or relationship preservation is important.

Potential candidates include:

* Users
* Messages
* Files
* Communities
* Conversations

The decision to use soft deletion shall depend on the data's lifecycle and privacy requirements.

#### 3.23.40 Deleted Message Behavior

When a message is deleted, the system may preserve a minimal record indicating that a message previously existed.

For example:

```text id="n5q8c3"
[Message deleted]
```

The exact behavior shall be defined by product requirements and privacy policies.

#### 3.23.41 Account Deletion

Account deletion shall consider related data.

Potentially affected information includes:

* Profile
* Messages
* Memberships
* Notifications
* Files
* Jam participation
* Audit records

The system shall distinguish between data that can be permanently deleted and records that must be retained for legitimate operational or legal reasons.

#### 3.23.42 Data Retention

Different data categories may have different retention policies.

```text id="h4m9r2"
Messages
Files
Notifications
Audit Logs
Security Logs
Temporary Data
Analytics Data
```

Retention periods shall be defined based on system requirements and applicable policies.

#### 3.23.43 Data Archiving

Large historical datasets may eventually be archived.

Potential archive candidates include:

* Old audit logs
* Historical notifications
* Old system events
* Inactive conversation data

Archiving should preserve data integrity and access controls.

#### 3.23.44 Data Export

Users may be provided with a mechanism to export applicable personal data.

Possible export contents include:

* Profile information
* Account settings
* Messages where appropriate
* Community memberships
* User-created content
* Activity information

Export operations may be processed asynchronously for large accounts.

#### 3.23.45 Data Import

Administrative or migration tools may support controlled data imports.

Imported data shall be validated before being written to production tables.

Import operations should provide:

* Validation
* Duplicate detection
* Error reporting
* Transaction safety
* Audit records

#### 3.23.46 Search Data

Search indexes shall not automatically become a separate source of truth.

The relational database shall remain the authoritative application data source unless a specific architecture defines otherwise.

Search indexes should be rebuildable from primary data where practical.

#### 3.23.47 Cache Data

Cache data shall not normally be treated as permanent application data.

If a cache is lost:

```text id="c8w2m6"
Cache Lost
   ↓
Application Requests Data
   ↓
Database / External Provider
   ↓
Cache Rebuilt
```

Critical information must remain available from persistent storage.

#### 3.23.48 Realtime Data

Realtime events shall not be treated as permanent storage.

For example:

```text id="x3r7n5"
jam.play
    ↓
Realtime Event
    ↓
Clients

Persistent Jam State
    ↓
Database
```

This allows clients to recover current state after disconnection.

#### 3.23.49 Data Consistency Model

The system shall distinguish between strongly persistent state and transient state.

Persistent state includes:

* Users
* Messages
* Communities
* Memberships
* Files metadata
* Notifications
* Jam state

Transient state may include:

* Typing indicators
* Connection status
* Temporary playback events
* Cache values

Transient state should not be relied upon for permanent records.

#### 3.23.50 Concurrency Control

The system shall consider concurrent updates.

Examples include:

* Two users editing community settings.
* Multiple users reacting to a message.
* Multiple Jam control events.
* Simultaneous membership changes.
* Multiple devices updating user settings.

Appropriate database constraints, transactions, version numbers, or conflict-handling mechanisms should be used where required.

#### 3.23.51 Jam Concurrency

Jam playback commands may arrive close together.

For example:

```text id="m8q4v2"
Host
 ├── PLAY
 ├── SEEK
 └── PAUSE
```

The system shall define ordering rules so stale events do not incorrectly replace newer playback state.

A state version or server-generated sequence can be used for ordering.

#### 3.23.52 Multi-Device Data Consistency

A user may be logged in from multiple devices.

Changes made on one device should propagate appropriately to other authorized devices.

Examples include:

* Profile changes
* Settings changes
* Read states
* Session revocation
* Notification state

Realtime events may be used to keep active clients synchronized.

#### 3.23.53 Data Access Control

Data access shall be controlled by the backend.

Examples include:

```text
Private Conversation
→ Conversation Members Only

Private Channel
→ Authorized Channel Members

Private Jam
→ Authorized Participants

Admin Data
→ Authorized Administrators
```

Database queries shall be scoped according to authorization requirements.

#### 3.23.54 Data Privacy

The system shall minimize unnecessary collection and storage of personal information.

Data should only be retained when it has a legitimate system purpose.

Sensitive information shall have appropriate:

* Access controls
* Encryption where required
* Retention policies
* Logging restrictions
* Deletion procedures

#### 3.23.55 Data Encryption

Data protection may occur at multiple layers.

```text id="p7m3r9"
Client
  ↓ HTTPS/TLS
API
  ↓
Database / Storage
```

Sensitive data requiring additional protection may use application-level encryption where justified.

Passwords shall use password hashing rather than reversible encryption.

#### 3.23.56 Database Security

Database access shall be restricted to authorized application services and administrators.

Production database credentials shall:

* Be stored securely.
* Not be committed to source control.
* Use least-privilege access.
* Be rotated when required.

#### 3.23.57 Database Backup Integration

The data architecture shall support the backup and recovery strategy defined previously.

Critical persistent data shall be included in backup procedures.

Caches and transient realtime events generally do not require the same backup treatment as primary application data.

#### 3.23.58 Data Migration

Schema and data migrations shall be version-controlled.

Migration processes shall support:

* Reproducibility
* Ordering
* Validation
* Rollback where practical
* Production safety

Large data migrations should be tested against production-scale datasets where possible.

#### 3.23.59 Data Lifecycle

A general data lifecycle shall be:

```text id="z4n8c2"
Create
  ↓
Store
  ↓
Use
  ↓
Update
  ↓
Archive / Retain
  ↓
Delete
```

The lifecycle shall vary depending on the data category.

#### 3.23.60 Data Ownership

Each major data category shall have a clear owning module.

Example:

| Data           | Primary Module          |
| -------------- | ----------------------- |
| Users          | User Management         |
| Profiles       | User Profile            |
| Messages       | Messaging               |
| Communities    | Community               |
| Channels       | Community               |
| Music Metadata | Music                   |
| Jam State      | Jam                     |
| Notifications  | Notification            |
| Files          | File/Media              |
| Audit Records  | Administration/Security |
| Settings       | User Settings           |

This separation supports modular architecture.

#### 3.23.61 Data Access Layer

The application should avoid scattering database logic throughout controllers.

The preferred architecture is:

```text id="k6r2m8"
Controller
    ↓
Application / Domain Service
    ↓
Repository / Model Layer
    ↓
Database
```

This supports testability and maintainability.

#### 3.23.62 Data Transfer Objects

Where appropriate, Data Transfer Objects or equivalent structures may be used to separate database models from API responses.

This helps prevent accidental exposure of internal fields.

#### 3.23.63 API Resource Transformation

Laravel API Resources or equivalent response transformers should control which fields are returned to clients.

For example, a user response should not automatically expose:

* Password hashes
* Internal security fields
* Private administrative metadata
* Internal database fields

#### 3.23.64 Pagination Strategy

Large datasets shall use pagination.

Cursor pagination may be preferred for high-volume chronological data such as:

* Messages
* Notifications
* Audit logs
* Activity history

Traditional page-based pagination may remain appropriate for smaller administrative datasets.

#### 3.23.65 Data Sorting

Sorting should use indexed fields whenever practical.

Common sorting fields include:

* `created_at`
* `updated_at`
* `name`
* `last_message_at`

The API should define supported sorting options rather than allowing arbitrary database ordering.

#### 3.23.66 Data Validation

Data shall be validated before persistence.

Validation shall occur at the API/application layer and be supported by database constraints where appropriate.

Validation examples include:

* Required fields
* Data types
* Length limits
* Allowed values
* Relationships
* Unique values
* File metadata

#### 3.23.67 Data Integrity Monitoring

The system should periodically detect data integrity issues.

Potential checks include:

* Orphaned records
* Invalid memberships
* Missing files
* Broken references
* Duplicate records
* Invalid Jam states

Detected inconsistencies should be investigated and corrected through controlled procedures.

#### 3.23.68 Data Architecture Evolution

The data architecture shall support future functionality.

Potential future entities may include:

* Playlists
* Follows
* Social feeds
* Creator profiles
* Collaborative playlists
* Voice channels
* Subscriptions
* Recommendations
* Analytics

New entities should follow the same principles of authorization, integrity, scalability, and lifecycle management.
