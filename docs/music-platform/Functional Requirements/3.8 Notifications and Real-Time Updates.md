### 3.8 Notifications and Real-Time Updates

The Notifications and Real-Time Updates module will provide users with timely information about activities occurring within the platform. The module will support both persistent notifications and temporary real-time updates.

Notifications may originate from messaging, group conversations, communities, user interactions, and Jam sessions. Real-time updates will allow connected clients to immediately reflect changes without requiring users to manually refresh the application.

The module will use the application's real-time communication infrastructure to deliver events to connected clients. Pusher will serve as the primary real-time provider for the initial implementation, while Laravel Reverb may be used as a development fallback where configured.

#### 3.8.1 Notification Types

The system shall support different notification categories based on the source of the activity.

Possible notification types include:

* New direct message
* Group message
* Mention
* Message reaction
* Reply or thread activity
* Group invitation
* Community invitation
* Community membership activity
* Community announcement
* Jam invitation
* Jam activity
* System notification
* Account or security notification

Additional notification types may be introduced as the system evolves.

#### 3.8.2 Persistent Notifications

Important notifications shall be stored in the database so users can access them even when they are offline.

A notification record may contain:

* Notification identifier
* Recipient identifier
* Notification type
* Related resource identifier
* Notification content
* Read status
* Creation timestamp
* Read timestamp where applicable

For example, a message mention may reference:

```text
Notification
├── recipient_id
├── type
├── message_id
├── conversation_id
├── read_at
└── created_at
```

#### 3.8.3 Real-Time Notifications

When a notification-producing event occurs, the system may deliver the notification to an actively connected user in real time.

Example:

```text
User A mentions User B
        │
        ▼
Laravel processes message
        │
        ├── Stores message
        │
        ├── Creates notification
        │
        └── Broadcasts event
                │
                ▼
             Pusher
                │
                ▼
          User B's client
                │
                ▼
       Notification appears
```

The real-time event does not replace persistent storage. The database remains the source for retrieving notification history.

#### 3.8.4 Notification Read Status

The system shall allow users to mark notifications as read.

The system may support:

* Marking one notification as read
* Marking multiple notifications as read
* Marking all notifications as read
* Retrieving unread notification count

The read state shall be synchronized with the backend.

#### 3.8.5 Unread Notification Count

The system shall provide an unread notification count where appropriate.

The count may be displayed in:

* Notification center
* Navigation menu
* Mobile navigation
* Desktop application
* Message interface
* Community interface

The count shall update in real time when a new notification is generated or an existing notification is marked as read.

#### 3.8.6 Messaging Notifications

Messaging-related notifications may be generated when:

* A user receives a direct message
* A user receives a group message
* A user is mentioned
* A user receives a thread reply
* A user receives a message reaction
* A relevant conversation activity occurs

The system may suppress or modify notifications when the user is already actively viewing the related conversation.

#### 3.8.7 Community Notifications

Community notifications may include:

* Community invitation
* New announcement
* Mention in a community channel
* Channel activity
* Role changes
* Moderation actions
* Community membership events

Community administrators may have additional notification events related to administrative activities.

#### 3.8.8 Jam Notifications

The system may generate notifications related to Jam sessions.

Examples include:

* Invitation to a Jam
* User joined a Jam
* User left a Jam
* Host ended a Jam
* Jam became available
* Other supported Jam activity

Jam playback synchronization itself shall remain a real-time state synchronization function rather than a persistent notification.

#### 3.8.9 Real-Time Event Categories

The application shall define standardized real-time events.

Possible event categories include:

**Messaging**

```text
message.sent
message.updated
message.deleted
message.reaction_added
message.reaction_removed
message.typing
message.read
```

**Presence**

```text
user.online
user.offline
user.presence_updated
```

**Groups**

```text
group.created
group.member_added
group.member_removed
group.updated
```

**Communities**

```text
community.created
community.member_joined
community.member_left
community.updated
channel.created
channel.updated
```

**Jam**

```text
jam.created
jam.joined
jam.left
jam.play
jam.pause
jam.seek
jam.track_changed
jam.ended
jam.state_updated
```

The event naming convention shall remain consistent throughout the application.

#### 3.8.10 Real-Time Channels

The system shall use appropriately scoped channels to prevent unauthorized users from receiving private events.

Possible channel structures include:

```text
private-user.{userId}
private-conversation.{conversationId}
presence-community.{communityId}
presence-jam.{jamId}
```

Channel authorization shall be performed by the backend.

A client shall not be considered authorized simply because it knows the channel name.

#### 3.8.11 User-Specific Events

Private user channels may be used for events intended for a specific user.

Examples include:

* Personal notifications
* Account events
* Invitation events
* Security events
* Personal presence updates

Example:

```text
private-user.125
```

Only the authenticated user associated with the channel should be allowed to subscribe.

#### 3.8.12 Conversation Events

Conversation channels may be used for real-time messaging activity.

For example:

```text
private-conversation.456
```

Events may include:

* New messages
* Message edits
* Message deletion
* Reactions
* Typing indicators
* Read state changes
* Thread activity

Only conversation members with appropriate access shall be authorized to subscribe.

#### 3.8.13 Presence Updates

The system may provide online and offline status for users.

Presence information may include:

* Online
* Offline
* Away
* Busy
* Last active time

Presence information shall be handled according to the platform's privacy settings.

The system shall avoid broadcasting unnecessary presence events at excessive frequency.

#### 3.8.14 Typing Indicators

The system shall support temporary typing indicators for conversations and threads.

For example:

```text
User A is typing...
```

Typing events should not normally be stored as permanent database records.

Instead, they should be transmitted through the real-time communication layer.

The client may automatically remove the typing indicator after a timeout or when a message is sent.

#### 3.8.15 Real-Time Reactions

Message reactions shall be synchronized in real time.

For example:

```text
User A adds 👍
        │
        ▼
Laravel validates reaction
        │
        ▼
Database updated
        │
        ▼
reaction_added event
        │
        ▼
Connected clients update UI
```

Removing a reaction shall similarly generate a real-time event.

#### 3.8.16 Real-Time Message Updates

The system shall support real-time synchronization of message changes.

Possible operations include:

* New message
* Message edit
* Message deletion
* Reaction addition
* Reaction removal
* Reply creation
* Read-state changes

Clients shall update their local interface based on the received event without requiring a full page refresh.

#### 3.8.17 Connection Recovery

The real-time client shall account for temporary connection failures.

When the connection is interrupted, the client should:

1. Detect the disconnection.
2. Attempt reconnection.
3. Re-authenticate private channels if required.
4. Re-subscribe to required channels.
5. Retrieve missed persistent data where necessary.
6. Synchronize the client state with the backend.

Real-time events should not be treated as the sole source of truth for persistent application data.

#### 3.8.18 Pusher and Reverb Configuration

The initial implementation shall use Pusher as the primary hosted real-time provider.

Development environments may optionally use Laravel Reverb as a fallback.

The application architecture should keep real-time event definitions independent from the underlying provider.

Conceptually:

```text
Application Event
       │
       ▼
Broadcasting Layer
       │
       ├── Pusher
       │
       └── Reverb
```

This allows the application to change its real-time infrastructure without redesigning individual messaging, community, or Jam features.

#### 3.8.19 Real-Time Provider Fallback

Where a client-side fallback mechanism is implemented, the application may attempt to use the primary real-time provider first and switch to the configured fallback provider when appropriate.

Example development configuration:

```text
Pusher
   │
   ├── Connected → Continue using Pusher
   │
   └── Failed → Attempt configured Reverb connection
```

The fallback mechanism shall not result in duplicate event processing.

The client shall also prevent the same event from being applied multiple times when reconnecting or switching providers.

#### 3.8.20 Event Idempotency

Real-time events may occasionally be delivered more than once due to reconnection or retry behavior.

The application should therefore provide mechanisms for identifying events uniquely.

An event may contain:

```json id="c4v8p2"
{
    "event_id": "evt_01JXYZ",
    "event": "message.sent",
    "resource_id": "msg_123"
}
```

The client can use the event identifier to avoid applying the same state change repeatedly.

#### 3.8.21 Notification Preferences

Users may be allowed to configure notification preferences.

Possible settings include:

* Direct message notifications
* Group notifications
* Mention notifications
* Reaction notifications
* Community notifications
* Jam notifications
* System notifications

Future versions may support separate preferences for:

* In-app notifications
* Email notifications
* Push notifications
* Desktop notifications
* Mobile notifications

#### 3.8.22 Notification Privacy

Notifications shall not expose information to unauthorized users.

The system shall validate:

* Recipient identity
* Resource access
* Conversation membership
* Community membership
* Jam membership
* Notification ownership

Sensitive information should not be included in events when the receiving client does not have permission to access the associated resource.

#### 3.8.23 Notification Performance

The system should minimize unnecessary real-time traffic.

Temporary events such as typing indicators and presence updates should not generate unnecessary persistent database writes.

Persistent notifications should be created only when required by the application's notification rules.

The system may use Redis or queue workers for notification processing when notification volume increases.
