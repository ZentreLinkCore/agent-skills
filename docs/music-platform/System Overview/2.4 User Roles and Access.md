### 2.4 User Roles and Access

The system will implement role-based access control to manage the permissions and responsibilities of different users. Access to system functions will depend on the user's assigned role and the context in which the user is performing an action.

The system will distinguish between platform-level roles and resource-specific roles. For example, a user may be a regular platform user while simultaneously serving as a Community Administrator or Jam Host for a specific resource.

#### 2.4.1 Role Definitions

| Role                        | Description                                                                                                                  |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **Regular User**            | Standard platform user who can communicate, participate in communities, discover music, and use supported platform features. |
| **Community Administrator** | User responsible for managing a specific community and its channels, members, and settings.                                  |
| **System Administrator**    | User responsible for platform-wide administration, system management, and administrative operations.                         |
| **Jam Host**                | User who creates and manages a specific Jam session.                                                                         |
| **Jam Participant**         | User who joins an existing Jam session and participates in synchronized listening.                                           |

#### 2.4.3 Resource-Based Permissions

In addition to general platform roles, certain permissions will be determined by the resource being accessed.

For example, a user may have administrative permissions within one community while remaining a regular member of another community. Similarly, a user may become a Jam Host only for the Jam session that they created.

This approach prevents users from receiving unnecessary platform-wide permissions while still allowing them to perform management functions within resources where they have responsibility.

#### 2.4.4 Permission Enforcement

Access control will be enforced on the backend rather than relying solely on the client interface. The backend will verify the authenticated user's identity, role, resource membership, and required permissions before processing protected actions.

For example, hiding a **Delete Community** button from a regular user is not sufficient security. When a request is sent to the API, the backend must independently verify whether the authenticated user has permission to perform the requested operation.

This approach will help prevent unauthorized access through manually constructed API requests or modified client-side behavior.

#### 2.4.5 Future Role Expansion

The role and permission architecture will be designed to support additional roles in future versions. Potential roles may include:

* Community Moderator
* Music Curator
* Content Creator
* Community Owner
* Verified User
* Platform Moderator

Additional roles will be introduced only when required by future system functionality and will follow the same role-based and resource-based access principles.
